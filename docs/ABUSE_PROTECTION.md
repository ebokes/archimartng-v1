# Public form abuse protection

The professional application and enquiry forms validate input on the server and use a hidden honeypot field. They do not currently limit request frequency. Archimart is intended to run on Vercel, so its WAF can count submissions at the edge without a new application dependency or database table.

## Reviewed Vercel rule (Log publication operator-reported; enforcement pending)

The operator reported on 18 November 2026 that the initial rule was published in **Log** mode. No dashboard configuration values, match counts, or traffic observations were supplied with that report, and the coding agent did not inspect Vercel. Treat the rule's effective scope and action-name matches as unverified until the operator provides the checks below. Log mode allows matched requests through; it does not enforce a rate limit.

The proposed **one** rate-limiting rule covers two public Server Actions. Source review of the operator-identified deployment commit `24d9a09ed4ba9f7303d4dc6a6d1041cb49a61f0a` confirms both exports and their honeypots. The application action is `submitProfessionalApplication` in `src/app/professionals/apply/actions.ts`, invoked by the form at `/professionals/apply`. The enquiry action is `submitEnquiry` in `src/app/enquiries/actions.ts`, invoked on both published plan and professional detail pages. Both are POST Server Actions, not dedicated API routes. Do not match only `/professionals/apply` or `/enquiries`: the latter is a source directory rather than the request path, and enquiry POST paths vary by listing. [Vercel supports Server Action Name matching from Next.js 15.5 onward](https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration); the deployment commit declares Next.js `^16.4.4`.

| Setting               | Proposed value                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Condition             | Server Action Name **is any of** the exact deployed names for `submitProfessionalApplication` and `submitEnquiry` |
| Additional conditions | Environment **equals** Production **AND** Method **equals** POST                                                  |
| Strategy              | Fixed window                                                                                                      |
| Counting key          | IP address                                                                                                        |
| Window and limit      | 10 matching requests per 60 seconds per IP, shared across both forms                                              |
| Follow-up action      | Log during observation; Default Too Many Requests (HTTP 429) after approval and a controlled Preview test         |

The expected name shape in Vercel is `app/.../actions.ts#exportName`, but **confirm the exact two configured values against Firewall traffic**; the source paths alone do not prove the deployed WAF values. Use `Is any of` for the two names, then AND the Environment and Method conditions. Confirm the saved rule preview shows that grouping. Do not include administrator actions. Counted requests include invalid and honeypot submissions because the rule runs before the Server Actions. A common IP is shared by several users, and both forms share the same counter. A 10-per-60-second fixed window is a provisional ceiling, not a measured traffic requirement; legitimate users behind one office or mobile network may reach it. Fixed windows can permit bursts near a boundary, and [Vercel tracks counters per region](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting), so this is a proportionate abuse safeguard rather than an absolute global cap.

Vercel documents fixed-window, IP-keyed WAF rate limiting on Hobby and Pro. Hobby allows **one rate-limiting rule per project**, within three total custom rules; Pro allows more. [Current limits and pricing](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) should be checked in the dashboard before approval. The actual Archimart plan, available rule slot, any existing rule precedence, and billing state were **not** verified from this repository.

## Configuration and cautious rollout

**Before considering 429:** Record the exact two Server Action Name values configured, a matched POST for **each** action on the intended environment, no unexpected GET/admin/auth matches, the observation period and highest matched requests from any one IP in a 60-second window, any legitimate-user false positives, and the actual plan/rule allowance. Report aggregates only; do not share IP addresses or form contents. If there is no traffic for one action, use one controlled honeypot submission on that form and confirm it matches. A quiet or empty log does not establish correct matching. Without these results, the 10/60 threshold cannot be judged against actual usage and Production enforcement is not ready for approval.

1. In Vercel Project → **Firewall → Overview**, look for the exact Server Action Name values in existing traffic if the dashboard exposes them. If the names are not shown, start the Log rule using the source-shaped candidates `app/professionals/apply/actions.ts#submitProfessionalApplication` and `app/enquiries/actions.ts#submitEnquiry`, then verify or correct them from matched traffic before enforcement. To generate a controlled match if needed, submit otherwise valid synthetic form data with the hidden `companyWebsite` field populated: both current and reviewed-deployment actions return before any database query or insert when that field is filled. Do not send credentials or personal data in test submissions.
2. Confirm the Vercel plan and spare rate-limiting rule slot. From **Firewall → Configure → New Rule**, name it `public-form-submissions`. Set **If** to `Server Action Name` **Is any of** the two confirmed or candidate values, **AND** `Environment` **Equals** `Production`, **AND** `Method` **Equals** `POST`. Set **Then → Rate Limit**, **Fixed Window**, **IP address**, **60 seconds**, **10 requests**, and follow-up **Log**. Do not add a persistent action. Review any pricing dialog. Save, then **Review Changes → Publish** only after explicit operator approval.
3. Inspect the Firewall overview's rule traffic for at least one 10-minute live window, preferably covering ordinary usage. Confirm both form actions actually match; if either does not, correct its name and repeat Log observation. Confirm GET navigation, authentication, and administrator actions do not match. Check request counts by IP for shared-network false positives. Log mode does not block or prove 429 enforcement.
4. For a controlled enforcement check, temporarily target only an isolated **Preview** environment and use a low limit such as **2 requests per 60 seconds**, with follow-up **429**. From one test IP, submit the application form three times with otherwise valid synthetic fields and `companyWebsite` populated; refresh after each success response. The honeypot returns before the insert, so these action requests should not create records. Confirm two allowed responses, then a 429 in browser Network/Firewall traffic; confirm a GET and an unrelated action remain unaffected. Do this only after separately approving the temporary Firewall changes. Restore the Production condition, 10/60 limit, and Log follow-up before the production decision. If Preview matching is unavailable, do not substitute a production flood test.
5. After reviewing the log period and Preview test, separately approve changing the Production follow-up to **Default Too Many Requests (429)**. Use **Save Rule → Review Changes → Publish**. Watch the Firewall overview and real form outcomes. If legitimate requests are limited, relax the threshold or return to Log while investigating; do not lower the threshold without traffic evidence.

The dashboard's **Review Changes → Publish** activates a Firewall change immediately and requires explicit approval under `AGENTS.md`. The coding agent did not configure or publish the operator-reported Log rule. Production 429 is not approved or active, based on the information supplied. The honeypot remains useful but is not a substitute for the rate limit.

## Rollback

If forms are affected, open **Firewall → Configure**, change the rule's follow-up back to **Log** or disable the rule, then **Save Rule → Review Changes → Publish** and confirm normal submissions resume. For a full configuration rollback, open **Firewall → ⋯ → View Audit Log**, select the prior known-good version, then **Restore → Restore Configuration**. Record the rule version, time, observed effect, and reason for rollback. [Vercel documents the audit-log restore path](https://vercel.com/docs/vercel-firewall/vercel-waf).
