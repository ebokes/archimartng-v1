# Archimart project context

## Product

Archimart is a Nigerian architecture marketplace targeting a functional MVP launch by 31 December 2026. Its business model is lead generation. Audiences are clients, architects, and builders. Clients browse plans and professionals and submit enquiries; professionals can apply for listings.

## Confirmed MVP decisions

- Administrators manage all plan listings and professional profiles.
- Professional verification and dashboard enquiry review are manual; there are no automated notifications.
- There are no client or professional accounts, online payments, escrow, subscriptions, ARCHI AI, BUILDTRACK, or ARCHIVE memberships in the MVP.

## Technical architecture and infrastructure

- Next.js App Router `^16.4.4`, React `^19.2.0`, TypeScript `^5.8.3`, Tailwind CSS `^4.2.1`, and Zod `^4.6.7`, per `package.json`. npm is the package manager.
- Neon PostgreSQL project `archimart`, with `development` and `production` branches.
- Drizzle ORM `^0.45.4` for application and authentication schemas; Better Auth `^1.7.15` for administrator email/password sessions.
- Local configuration uses `DATABASE_URL` (pooled), `DATABASE_URL_DIRECT` (direct), `NEON_DEVELOPMENT_ENDPOINT_ID`, `BETTER_AUTH_URL`, and `BETTER_AUTH_SECRET`. Plan image uploads additionally require `PLAN_IMAGE_ENV` and the matching R2 endpoint, bucket, public base URL, region, access key ID, and secret access key variables listed in `.env.example`. Keep values in ignored local environment files; never record credentials here.

## Production deployment readiness audit (10 November 2026)

This was a repository-only review. No Vercel settings, deployed pages, Neon branch, database rows, or production logs were inspected. All 24 local tests, lint, and TypeScript passed. There are no repository browser end-to-end tests or CI workflow files.

- **Authentication and authorization:** `src/lib/auth.ts` disables public email/password sign-up and the sign-up route, uses database-backed sessions with cookie caching off, and checks for an active `admins` record before creating a session. `requireAdmin()` checks the session and active allow-list record on protected server operations. The auth route runs on Node.js. Production still needs a runtime check of sign-in, sign-out, anonymous rejection, disabled sign-up, inactive-admin denial, and secure session-cookie behavior. The code accepts HTTP or HTTPS `BETTER_AUTH_URL`; the production value must be the exact HTTPS site origin and use a unique, secret `BETTER_AUTH_SECRET` of at least 32 characters. Neither deployed value was inspected.
- **Database and provisioning:** The repository contains ordered migrations `0000_round_maestro`, `0001_empty_energizer`, and `0002_orange_demogoblin`, including the nullable proposed biography column. Their application to production is **unknown**. Runtime clients use `DATABASE_URL`; the development endpoint assertion runs outside production, so it does not establish which Neon branch the deployed URL targets. `drizzle.config.ts` and `scripts/provision-first-admin.ts` are intentionally guarded for the verified development endpoint and are **not** production migration or provisioning procedures. A separately reviewed, explicitly approved production migration and first-admin provisioning process is required; the production auth identity and active `admins` row must match. No production admin is confirmed.
- **Environment separation:** `.env.local` and `.vercel` are ignored by Git. Only `.env.example` is tracked. Confirm in Vercel that Production uses the intended production Neon pooled URL, while Preview and local development cannot silently use that branch. Reserve `DATABASE_URL_DIRECT` for an approved migration process; production runtime code needs the pooled `DATABASE_URL`, `BETTER_AUTH_URL`, and `BETTER_AUTH_SECRET`. Confirm the secret is distinct from development and that no credentials use `NEXT_PUBLIC_` names. No deployed environment values were read.
- **SEO and public content:** `robots.ts` and `sitemap.ts` require a valid HTTPS `NEXT_PUBLIC_SITE_URL`; otherwise crawling is blocked and the sitemap is empty. With a valid origin, the sitemap includes only published listings, and robots excludes admin and auth paths. The site URL and crawler output were not checked against the deployment. Public plan image URLs also need a live load check; R2 uploads remain disabled until configured, while URL covers remain available.
- **Abuse and data handling at audit time:** Public applications and enquiries used server-side validation and honeypots but had no active rate limit. `docs/ABUSE_PROTECTION.md` proposes one Vercel WAF rule for both actions; activation and any pricing require approval. Enquiries record explicit consent and a version. At the time of this audit, the repository had no published privacy page or data-retention procedure for applicant and enquiry contact information.

Run a controlled browser checklist on the deployed origin after schema and admin setup: anonymous admin rejection; sign-in/out; draft visibility; public listing and image rendering; application biography through review and private draft; enquiry through admin review and notes; and mobile layout. The operator supplied `archimartng@gmail.com` as the official privacy and data-request contact, and it is published in the notice. The operator still needs to adopt and perform a manual retention process. No record was deleted or database accessed for this task.
- **Proposed operating schedule, not yet active:** Review `submitted`/`under_review` applications and `new`/`in_progress` enquiries at least every 90 days; record whether follow-up is still needed. Delete rejected applications 12 months after final review, and approved applications 12 months after their profile is created, while keeping the separately managed public profile only as long as it remains needed. Reassess approved applications without a linked profile every 90 days. Delete spam enquiries after 30 days and closed enquiries 12 months after closure or last follow-up. Delete internal review notes with their parent record. These periods are product proposals, not claims about legal minimums or current enforcement.
- Before adopting the schedule, define how to verify and handle access, correction, and deletion requests; document any justified hold; confirm how database backups age out; and add an approved operator procedure for manual deletion. The schema has timestamps and statuses, but no dedicated closure timestamp or deletion job. Do not silently purge active cases, linked profiles, or records under a justified hold. The [Nigeria Data Protection Commission's published privacy principles](https://erp.ndpc.gov.ng/privacy_policies) support keeping personal data no longer than necessary, but this proposal still needs operator and legal review for Archimart's circumstances.
- The local database settings passed the verified development-endpoint guard before building. All 24 existing tests, lint, TypeScript, and `npm run build -- --webpack` passed; the build lists `/privacy` as a static route. No production operation, migration, or database record change was made.
