# Archimart V2 Phase 1: account lifecycle and schema proposal

**Status:** Design complete and additive migration `0003` applied to the verified Neon development branch on 18 November 2026 after explicit approval. A local-only client registration page, action and gated session policy are prepared but disabled by default as of 19 November. The [V2 PRD](ARCHIMART_V2_PRD.md) is still a draft; its five confirmed product decisions are inputs, while other stakeholder choices remain open.

## Existing boundary

- Better Auth owns `auth.user`, `auth.account`, `auth.session` and `auth.verification`; its user IDs are text. `auth.user.email` is unique and has `email_verified`. Password hashes remain in Better Auth's credential table.
- `src/lib/auth.ts` still disables the mounted Better Auth sign-up endpoint. Its session hook keeps administrator-only admission outside local development and uses the reviewed client admission policy locally; client admission requires a separate flag that remains off. `requireAdmin()` repeats the active allow-list check for each protected administrator operation. The first administrator is created by an operator-only command. These protections must stay effective throughout rollout.
- `professionals` holds administrator-managed public content, publication and verification states. `professional_applications` holds applicant details, review status and an optional linked profile. Neither table proves account ownership. The existing marketplace authorization helper is a policy primitive with no database or route integration.
- No separate V2 implementation plan was present in the repository before this file. The IDE's `docs/ff.md` and the older `PLAN.md` were not present in the checked workspace.

## Proposed identity model

Use the existing Better Auth identity and sessions. Add an application-owned `marketplace_accounts` row for each **non-administrator** identity, with exactly one role: `client` or `professional`. The role is server-assigned; it is never accepted from a sign-up request or mutable by the account holder. An auth identity with **any** `admins` row, including an inactive one, cannot acquire a marketplace account. An identity with a marketplace account cannot be added to `admins`. Administrator provisioning remains private and must reject an existing marketplace identity.

Public registration may create a **client** identity only. A user who wants to practice as a professional starts professional onboarding from that verified identity; the server changes its role to `professional` when onboarding is accepted for review. The operator approved one marketplace role per identity for V2.1; multi-role support is deferred. This avoids exposing a role-selecting Better Auth sign-up endpoint. A direct call to Better Auth sign-up must never create an administrator or an approved professional. If the Better Auth user is created but the application account row is not, it is inert: session creation and every marketplace operation reject the missing row. Implement a tested, idempotent account creation and recovery path and inspect the installed Better Auth hooks/transaction behavior before enabling sign-up. Do not assume its user-create hook and a separate application write commit atomically. Do not attach an unconditional `user.create.after` client-row insert: the operator-only administrator provisioner also creates a Better Auth user and must not receive a marketplace role.

The current session-create hook must eventually admit a user with **either** an active administrator allow-list row **or** an eligible marketplace account row, and reject an identity with both or neither. It must reject suspended/closed accounts and require verified email for marketplace sessions. `requireAdmin()` stays unchanged in meaning and continues checking `admins` on every protected administrator read and write. Client/professional operations use a separate session, account, role and object ownership check on every server operation. A pre-existing admin whose Better Auth `email_verified` flag is false must not be locked out by a blanket verification setting; inspect existing administrator identity state in an approved development-only verification step before changing global Better Auth options.

Better Auth documents email verification callbacks and `emailAndPassword.requireEmailVerification`, password-reset callbacks, and session revocation. Resend delivery is now configured behind development and production guards; development verification delivery was checked below. Keep sign-up `autoSignIn: false`; send verification only through the reviewed mail path, use bounded tokens and safe redirect origins, and revoke other sessions after password reset. Because the existing administrator may be unverified, prefer explicit marketplace session/operation verification checks until the global setting is proven compatible with current administrators. Password-reset delivery and session revocation still need separate testing. See [email verification](https://better-auth.com/docs/concepts/email), [email/password and reset](https://better-auth.com/docs/authentication/email-password), and [sessions](https://better-auth.com/docs/concepts/session-management).

## Proposed lifecycle

| Actor        | State / transition                           | Authorized actor and effect                                                                                                                                                                                                                             |
| ------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Client       | Registration → unverified                    | Public email/password registration creates an auth identity and a server-assigned client row; no automatic session. Duplicate-email responses remain generic.                                                                                           |
| Client       | Unverified → active                          | Verified email permits sign-in and client operations. Profile and future records remain scoped to the auth subject.                                                                                                                                     |
| Client       | Active → suspended → active                  | Administrator suspends or restores access with a recorded reason. Revoke sessions on suspension; every operation still checks status.                                                                                                                   |
| Client       | Active/suspended → closed                    | Verified request and administrator-reviewed closure; revoke sessions, block sign-in, and follow the approved privacy/retention process. Closure does not imply immediate erasure of records with lawful retention needs.                                |
| Professional | Verified client → onboarding                 | Authenticated user chooses professional onboarding. Server converts the role to professional and creates a pending professional account. No professional capability is granted. Existing public application submissions remain separate from this step. |
| Professional | Pending → approved or rejected               | Administrator reviews identity, qualifications and any application, records decision/reason, and may approve or reject. Approval alone neither publishes nor verifies a public profile.                                                                 |
| Professional | Rejected → pending                           | Revised submission may be considered after administrator review; record the new review event. No automatic approval.                                                                                                                                    |
| Professional | Approved → suspended → approved              | Administrator controls suspension/restoration and revokes sessions on suspension. Approved-only operations remain denied while suspended.                                                                                                               |
| Professional | Pending/rejected/approved/suspended → closed | Administrator-reviewed closure and retention handling; revoke sessions and remove active ownership capabilities without silently deleting the public listing or review evidence.                                                                        |

Email verification is a separate Better Auth identity property, not a professional approval state. Account activity, professional approval, public listing publication, and manual verification are independent checks. An unverified email cannot use marketplace operations; a pending/rejected professional may see only their own onboarding and decision status after email verification. A suspended/closed account cannot use protected operations even with a still-valid cookie. Suspension belongs to account status; approval uses only `pending | approved | rejected`.

The server-only marketplace authorization helper now takes the verified-email flag and subject from a server-validated Better Auth identity, then obtains role, account status and approval through a trusted account resolver. It exposes separate client, professional-onboarding and approved-professional entry points, so the protected operation selects its access level. Only an active client with no professional approval row may use client access; only active pending/rejected professionals may use onboarding access; only active approved professionals may use approved-professional access. Missing or inconsistent account/approval rows, another subject, unverified email, suspension and closure all fail with generic `Unauthorized` or `Forbidden` errors. Approved professionals use their own approved access path rather than onboarding. A listing's publication or verification state cannot grant account access. No database resolver or route uses this helper yet; future integration must provide account state from database rows and check object ownership separately.

The pure policy in `src/lib/marketplace-account-lifecycle.ts` permits only `active → suspended/closed` and `suspended → active/closed` for account status, and `pending → approved/rejected` and `rejected → pending` for professional approval. All these decisions require an administrator identity and a nonblank reason. No-op changes, reopening closed accounts, and downgrading an approved professional to rejected are prohibited. A verified active client may start their own onboarding; another identity cannot do it for them. A profile claim additionally requires an active, email-verified, approved professional account, no existing owner on either side, a reviewed administrator decision and reason, and a match if a linked application identifies a profile. These functions only decide eligibility; future actions must obtain the administrator through `requireAdmin()`, re-read rows in a transaction, enforce uniqueness and write the audit event.

## Additive PostgreSQL schema prepared for review

`src/db/schema.ts` defines the three new tables. Offline generation produced `drizzle/0003_v2_marketplace_accounts.sql`; it follows journal entry `0002` and was applied to **development only** after explicit approval. The SQL creates four enums, three tables, nine foreign keys, one unique column constraint, two unique indexes, seven ordinary indexes, and seven check constraints. It does not alter existing V1 or Better Auth tables. The summary below includes the additional review and claim attribution fields in the generated schema.

| `marketplace_accounts`        | `id uuid` PK; `auth_subject text` NOT NULL UNIQUE FK → `auth.user.id` **RESTRICT**; `role` enum (`client`, `professional`) NOT NULL; `status` enum (`active`, `suspended`, `closed`) NOT NULL; `created_at`, `updated_at`, nullable `suspended_at`, `closed_at`; index `(role, status)`.                                                                                                                                                                                                                                                                                                                                                                                                                               | One role and lifecycle per non-admin identity. Indexes cover account/date, admin/date and profile. Checks require admin attribution and a nonblank reason for non-onboarding events, and a profile ID only for a claim event.                                                                                                                                                                       | Restricted review, suspension, restoration, closure and profile-claim evidence. Onboarding may have no admin actor; sensitive decisions require one. Define retention and access rules before release.                                                        |

`auth.user` already stores name and unique email; do not duplicate them merely to create a `client_profiles` table. Add a client profile only when Phase 1 needs independently editable client-specific fields. Do not put password hashes, admin status, public verification, or publication in the new tables. Existing `professionals`, `professional_applications`, and V1 enquiries stay intact. The professional account's `profile_id` is the single source of profile ownership; do not add a second owner column to `professionals` without a later reason. Enforce `professional_accounts` → professional-role consistency in the transaction and server authorization; review a database-level enforcement option before migration approval. Unique nullable `profile_id` prevents two accounts from claiming one profile.

**Migration review concerns:** The database enum stores exactly one marketplace role per account, but a simple FK cannot prove that a `professional_accounts` row points to a marketplace row with role `professional`, nor exclude an identity already present in `admins`. Registration, administrator provisioning and every protected operation must enforce these invariants in trusted server transactions; consider a composite role FK or another database guard before approving the migration if database-level enforcement is required. A stored claim link and admin ID are evidence, not access by themselves: the later action must call `requireAdmin()`, verify the administrator is active, check current email verification/account state and profile ownership, then write the link and event in one transaction. Client account suspension/closure has no event row in this professional-only event table; define its restricted audit trail before those operations are enabled. The enum checks and attribution checks do not replace transition policy or session revocation.

**Final safety review:** Before enabling any V2 registration or account operation, both identity-creation paths must serialize checks for the same auth subject (for example, lock the `auth.user` row in their transactions) and reject either an `admins` row of any status or a marketplace row on the opposite path. New sessions and every protected administrator and marketplace operation must fail closed if both memberships appear, including with an existing session. Onboarding must atomically change a trusted client role to professional and insert the pending professional row. A profile claim must use `requireAdmin()`, re-read verified email, active account, professional role, approved status, application and current owner in one transaction, conditionally link the previously unowned profile, and write the attributed event. The unique profile index resolves competing claims; email or name matching never authorizes ownership. These safeguards are design requirements, **not implemented controls**. The development migration does not authorize V2 account access; public sign-up remains disabled.

## Existing profile claim and migration path

1. Keep all existing listings and applications unowned. No automatic link by email, name, phone, slug, or portfolio URL; these are evidence for review, not proof of control.
2. An email-verified professional requests association with a specific existing profile or an approved application. If an application already links to a profile, use that ID only as a candidate. If there is no application, an administrator-created profile can still be claimed after separate identity evidence review.
3. An active administrator checks identity/qualification evidence through a restricted process, confirms the profile has no owner, and records the decision. Profile publication and verification remain administrator-controlled and unchanged by the claim.
4. In one database transaction, re-read account, application and profile; require professional role, eligible approval, no existing account/profile link, and any application/profile match. Conditionally set `professional_accounts.profile_id` only when null; the UNIQUE constraint rejects races. Write a claim event with administrator ID and timestamp in the same transaction. Never accept a `profile_id` supplied by an untrusted request as sufficient authority.
5. Until an approved claim exists, the professional cannot edit a listing. An approved account with no profile may use account/status pages only. A legacy application may still be deleted on its approved V1 schedule; preserve the minimal claim decision event and separately define its retention.

The exact evidence standard, sensitive-field review, and ability to reclaim a disputed profile require stakeholder approval. For the first release, keep public verification status, publication status, slug, and sensitive contact fields administrator-controlled. Treat professional editing of other fields as a later, reviewed permission rather than inheriting the V1 administrator form.

## Server permission checks

| Operation                                         | Required checks                                                                                                                                                                       |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Administrator operations                          | Better Auth session, active `admins` row, and the existing `requireAdmin()` inside each read/action. Public account role is never an admin grant.                                     |
| Client own account                                | Better Auth session, verified email, matching active client account; object ID must belong to that account. No email-based ownership lookup.                                          |
| Professional onboarding/status                    | Better Auth session, verified email, matching active professional account; read only that account's application/review state.                                                         |
| Approved professional profile view/edit           | All onboarding checks plus `approval_status = approved`, `profile_id = requested profile.id`, and allowed field policy. Publication and manual verification fields remain admin-only. |
| Suspension, approval, claim, restoration, closure | Active administrator, current-state precondition, reason where applicable, transaction and audit event; revoke affected sessions for suspension/closure.                              |

`requireAdmin()` and the marketplace authorization helpers are policy checks, not a replacement for record ownership checks. Every server action and data loader must re-read the current state. UI hiding and middleware redirects are convenience only.

## Acceptance criteria before Phase 1 release

- Anonymous/direct sign-up cannot create an administrator, assign a professional role, or produce an approved account. Admin provisioning cannot reuse a marketplace identity.
- New clients verify email, sign in/out, recover passwords, and reach only their own account and dashboard. Missing and unverified account rows deny access.
- Professionals can register, complete onboarding and see only their own review state. Pending/rejected/suspended accounts cannot use approved capabilities; administrators can review and record decisions.
- No profile is auto-claimed from V1 data. Only a reviewed admin transaction links one account to one profile; cross-profile edits and simultaneous claims are denied.
- Professional approval, profile publication, and verification badges remain separate; professionals cannot set publication or verification. Existing administrators retain their allow-list access.
- Suspension/closure blocks every protected operation, revokes sessions, and produces a restricted audit event. Privacy notice and account-data retention rules are reviewed before collecting new V2 data.
