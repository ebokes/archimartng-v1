# Archimart V1 quality audit

**Date:** 12 November 2026. **Original scope:** repository and existing local build artifacts only. Follow-up F5 closure uses operator-reported deployment configuration checks, not agent access to Vercel or Neon. No production database, secrets, or personal records were inspected by the coding agent. Existing development browser results are documented in `ARCHIMART_CONTEXT.md`; this audit did not repeat them. No application code or dependencies were changed.

The review uses [OWASP ASVS 5.0 authentication](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md), [session management](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md), [anti-automation](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x11-V2-Validation-and-Business-Logic.md), and [browser security headers](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md) as assessment references, not as a claim of certification. ASVS 5.0 V2.4.1 calls for controls against excessive function calls; V3.4 covers response headers; V7.1 calls for a documented session lifetime policy. [Next.js production guidance](https://nextjs.org/docs/app/guides/production-checklist) informs the performance review.

## Verified controls and boundaries

- `src/lib/auth.ts:41-49` disables email/password sign-up and the sign-up path, uses database sessions, and disables cookie caching. `src/lib/auth.ts:50-69` blocks session creation without an active allow-list record. `src/lib/require-admin.ts:10-20` checks the current session and active administrator for protected operations. The reviewed admin query and action functions call it, including object-ID routes. All administrators have the same intended MVP role; no finer object ownership rule is required by the documented product model. This is source evidence, not a production penetration test.
- Public profile queries explicitly select display fields and require `published` (`src/lib/professionals.ts:8-47`). Plan queries filter publication (`src/lib/plans.ts:8-43`). Drizzle binds query parameters, and plan creation/update and application-to-profile linking use transactions (`src/app/admin/plans/actions.ts:90-109`, `:132-176`; `src/app/admin/professionals/actions.ts:115-150`). The linked-profile update has a conditional compare-and-set to prevent duplicate linkage.
- Public forms use Zod input bounds, honeypots, explicit enquiry consent, and a published-target check (`src/app/professionals/apply/actions.ts:37-49`; `src/app/enquiries/actions.ts:34-83`). Admin sign-in shows a generic failure message (`src/app/admin/sign-in/sign-in-form.tsx:25-38`). `.env.local` and `.vercel` are ignored; only `.env.example` is tracked (`.gitignore:5-10`). No secret values were read for this audit.
- [Better Auth's documented cookie defaults](https://better-auth.com/docs/concepts/cookies) include HttpOnly and production Secure cookies, with SameSite Lax; [its security reference](https://better-auth.com/docs/reference/security) describes origin and CSRF checks. These library properties were not verified against a deployed response. The configured `BETTER_AUTH_URL` accepts HTTP as well as HTTPS (`src/lib/auth.ts:22-31`), so the deployed value matters.

## Findings, ranked by risk and impact

**Deferred V1 follow-up:** F1 and the remaining non-blocking quality improvements are paused while V2 Phase 1 begins. Preserve their severity and recommendations for later review. F5 was closed through operator verification. Severity describes potential impact, while each finding states what was actually verified.

### F1 — Public submissions lack a verified rate limit

- **Category / severity / status:** Security / **High** / **Deferred — Unresolved** as of 18 November 2026. Log-mode rule publication was operator-reported; effective matching and enforcement remain unverified.
- **Evidence:** Both public Server Actions accept valid submissions after Zod and a honeypot (`src/app/professionals/apply/actions.ts:37-49`; `src/app/enquiries/actions.ts:34-83`). Neither action counts requests. The operator reports a published Vercel Log rule, but has not supplied its effective conditions or match observations. Log mode does not block submissions. Unlimited automated valid submissions could fill private review queues and increase database costs. No live abuse test was run by the coding agent.
- **Preparation on 12 November 2026:** The operator-identified deployment commit `24d9a09ed4ba9f7303d4dc6a6d1041cb49a61f0a` contains both exported actions and their pre-write honeypot exits. `src/app/professionals/apply/application-form.tsx:12-16,30-35` invokes the application action; `src/components/enquiry-form.tsx:11-20,34-39` invokes the enquiry action from both published listing detail pages. Vercel's [Server Action Name condition](https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration) supports the declared Next.js version. The exact deployed action-name strings and actual Vercel plan/rule slot were not observable here. [Vercel's rate-limit limits](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) support one fixed-window IP rule on Hobby; the proposed 10 matching POSTs per 60 seconds is a cautious starting value, subject to log-mode traffic review. Both actions share the counter; shared IPs, failed submissions, and per-region counters limit its precision. `docs/ABUSE_PROTECTION.md` now specifies the exact dashboard fields, log-first and isolated-Preview test sequence, approval gates, and rollback.
- **18 November 2026 evidence boundary:** The operator reports initial Log-mode publication, but no exact configured identifiers, matched POSTs for each action, unexpected-match review, one-minute per-IP peak, or plan/billing details were provided. The coding agent did not access the Vercel dashboard. The proposed 10 requests per 60 seconds per IP is a plausible starting ceiling, but its suitability cannot be established from absent traffic data. The Log publication alone does not support switching Production to 429. `docs/ABUSE_PROTECTION.md` lists the evidence needed, isolated-Preview 429 check, monitoring criteria, and rollback.
- **Recommended fix:** When V1 quality work resumes, verify both deployed action-name matches and rule scope in the published Log traffic, review ordinary-traffic per-IP peaks and false positives, then safely test 429 on isolated Preview. Seek separate approval before Production enforcement and monitor for false positives afterward. Use a shared counter if application-level throttling is later required; an in-memory counter is insufficient across serverless instances. **F1 remains unresolved** until enforcement is active and verified.
- **Complexity:** Small to medium operational change. **Timing:** Before public V1 launch.

### F2 — Administrator sign-in throttling may not be shared across Vercel instances

- **Category / severity / status:** Security / **Medium** / potential distributed-control gap, not a confirmed brute-force vulnerability.
- **Evidence:** `src/lib/auth.ts:33-70` does not configure `rateLimit` or shared storage. [Better Auth options](https://better-auth.com/docs/reference/options) say production rate limiting is enabled by default but its default storage is process memory. On multiple serverless instances, counters may be separate. The actual deployed instance pattern and edge protections were not inspected.
- **Recommended fix:** Confirm the deployed sign-in limit with safe, controlled testing; document the control. If it is insufficient, use a supported shared rate-limit store or a narrowly scoped edge rule, avoiding conflict with the pending public-form rule.
- **Complexity:** Medium if shared storage is needed. **Timing:** Before public V1 launch.

### F3 — Application security headers are not configured in the repository

- **Category / severity / status:** Security / **Medium** / confirmed source omission; deployed headers unverified.
- **Evidence:** `next.config.ts:3-15` has no `headers()` policy. The root layout adds an inline theme script (`src/app/layout.tsx:45-53`), which needs deliberate handling under a restrictive CSP. No repository policy sets CSP, frame-ancestors, HSTS, nosniff, or Referrer-Policy. Vercel may add some headers independently; no response was inspected.
- **Recommended fix:** Inspect deployed response headers first. Add missing headers using [Next.js header configuration](https://nextjs.org/docs/app/api-reference/config/next-config-js/headers) or reviewed deployment settings. Test a CSP in report-only mode and account for the theme script before enforcement; avoid assuming a blanket policy will work.
- **Complexity:** Medium. **Timing:** Before public V1 launch for a basic reviewed policy; CSP refinement can follow measured compatibility testing.

### F4 — Administrator session lifetime policy is implicit

- **Category / severity / status:** Security / **Medium** / confirmed policy gap; exploit unverified.
- **Evidence:** `src/lib/auth.ts:47-49` only disables cookie caching; it does not set or document an inactivity or absolute session lifetime. [Better Auth documents](https://better-auth.com/docs/concepts/session-management) a seven-day sliding default. `docs/ARCHIMART_CONTEXT.md` and `AGENTS.md` do not define a maximum concurrent-session or reauthentication policy. Long-lived admin sessions increase impact if a device or cookie is lost; session validation itself remains server-side.
- **Recommended fix:** Decide and document administrator inactivity, absolute lifetime, concurrent-session, and revocation behavior; configure supported Better Auth settings where needed. Verify Secure, HttpOnly, SameSite, and sign-out behavior on the deployed HTTPS origin.
- **Complexity:** Small to medium. **Timing:** Decide before public V1 launch.

### F5 — Production environment separation verified by operator

- **Category / severity / status:** Security / **High** / **closed through operator verification on 12 November 2026**. The coding agent did not independently inspect Vercel or Neon configuration.
- **Confirmed repository and local evidence:** The intended Neon project is `archimart`, with `development` for local/Preview work and `production` for the live deployment (`docs/ARCHIMART_CONTEXT.md`). Runtime database clients use `DATABASE_URL` and check the development endpoint only when `NODE_ENV !== 'production'` (`src/db/index.ts:7-21`; `src/db/auth-client.ts:7-24`). The guard compares the pooled and direct Neon endpoint hosts, database path, and username to `NEON_DEVELOPMENT_ENDPOINT_ID` (`src/db/development-branch.ts:1-50`); it cannot independently establish the endpoint's branch name. Drizzle Kit loads `.env.local`, runs that guard, and uses `DATABASE_URL_DIRECT` (`drizzle.config.ts:5-17`). A local metadata-only check found both database URLs present and matching the configured endpoint ID, a localhost auth origin, an auth secret of at least 32 characters, and no local `NEXT_PUBLIC_SITE_URL`; it did not print values or connect to either database. `.env.local` is ignored and is not tracked (`.gitignore:5-10`).
- **Operator-confirmed deployment evidence:** The operator checked the current deployments at commit `24d9a09ed4ba9f7303d4dc6a6d1041cb49a61f0a` and reported matches for Production `DATABASE_URL` → Neon `production`, every enabled Preview `DATABASE_URL` → an isolated non-production branch, configured direct URLs → their corresponding branches, `BETTER_AUTH_URL` → each correct HTTPS origin, appropriate `NEXT_PUBLIC_SITE_URL` assignments, distinct Production/Preview `BETTER_AUTH_SECRET` values, and inclusion of those settings in the current deployments. These are operator-reported checks, not independently inspected Vercel or Neon metadata. No values, endpoint IDs, or credentials were shared. Production schema and administrator state remain separate launch checks.
- **Expected mapping:** Vercel **Production** should use a pooled `DATABASE_URL` whose endpoint belongs to Neon's `production` branch, an independently generated `BETTER_AUTH_SECRET` (at least 32 characters), and HTTPS origin-only `BETTER_AUTH_URL` and `NEXT_PUBLIC_SITE_URL` matching the canonical production domain. **Preview** should use the `development` branch or an isolated Preview branch, never the production endpoint; its auth secret should differ from Production's and its HTTPS auth origin should match the actual Preview host used for sign-in. Leave `NEXT_PUBLIC_SITE_URL` unset in Preview unless deliberate indexing is approved: a valid HTTPS value enables public robots and sitemap output (`src/lib/site-url.ts:1-24`; `src/app/robots.ts:7-16`; `src/app/sitemap.ts:9-14`). **Local** uses development pooled/direct URLs, verified development endpoint ID, a localhost Better Auth origin, and its own secret. `DATABASE_URL_DIRECT` belongs to the reviewed migration workflow, not ordinary Vercel runtime. `.env.example:9-10` says to leave the local site URL blank but contains a real deployment origin; copying it unchanged would contradict that instruction.
- **Boundary:** [Next.js sets `NODE_ENV` to `production` for `next build`](https://nextjs.org/docs/messages/non-standard-node-env), so the local development guard is not a Preview isolation mechanism. F5 is closed for the checked deployment configuration through the operator's explicit branch and secret verification. Recheck only if deployment variables, Neon branch wiring, or the serving deployment changes; [Vercel variable changes apply to new deployments](https://vercel.com/docs/environment-variables/managing-environment-variables). No production database or deployed application endpoint was contacted by the coding agent.
- **Complexity:** Medium operational review, completed by operator. **Timing:** Recheck after relevant configuration changes.

### F6 — Local dependency audit contains moderate development-tool advisories

- **Category / severity / status:** Security / **Medium** / confirmed advisory report; deployed exploitability unverified.
- **Evidence:** Read-only `npm audit --json` reported **11 moderate, 0 high, 0 critical** findings. `npm audit --omit=dev --json` still reported four moderate nodes in the Drizzle Kit → `@esbuild-kit` → `esbuild` chain. `package.json:85` lists Drizzle Kit as a dev dependency; `npm explain drizzle-kit` also shows it as Better Auth's optional peer, which explains why the omit-dev report is not proof that the CLI ships in a production function. The underlying [esbuild advisory](https://github.com/advisories/GHSA-67mh-4wv8-2f99) concerns a development server; the separate [minimatch advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249) appears in lint tooling.
- **Recommended fix:** Inspect the deployment trace, review patched compatible tool versions, and update through normal dependency review. Do not apply the audit's suggested major downgrade automatically. Keep development servers private.
- **Complexity:** Small to medium. **Timing:** Triage before launch; upgrade can wait if the affected CLI is absent from deployed functions.

### F7 — Public and administrator lists load without a bound

- **Category / severity / status:** Performance / **Medium** / confirmed query pattern; impact depends on record count.
- **Evidence:** `src/lib/plans.ts:8-29`, `src/lib/professionals.ts:8-24`, `src/lib/enquiries.ts:8-23`, and `src/lib/professional-applications.ts:8-24` return every matching row. The homepage then takes only three plans in memory (`src/app/page.tsx:12-18`), while the sitemap repeats both full catalogue reads (`src/app/sitemap.ts:12-25`). Admin lists of applications and enquiries contain personal information, increasing response size as records grow.
- **Recommended fix:** Limit the homepage query to three at SQL level. Add cursor or page-based limits to catalogue and admin lists when row counts justify them; keep the sitemap complete with a separate bounded or streaming strategy. Measure counts and response sizes before choosing page size.
- **Complexity:** Medium. **Timing:** Homepage limit before launch is inexpensive; full pagination can wait for growth.

### F8 — Dynamic rendering and duplicate detail reads increase database work

- **Category / severity / status:** Performance / **Medium** / confirmed source pattern; live latency unmeasured.
- **Evidence:** Public home, catalogue, and detail routes force dynamic rendering (`src/app/page.tsx:9`; `src/app/plans/page.tsx:6`; `src/app/professionals/page.tsx:16`; both detail pages at line 8). `generateMetadata` and the page each call the same Drizzle detail query (`src/app/plans/[slug]/page.tsx:16,30`; `src/app/professionals/[slug]/page.tsx:16,30`); these are not automatically memoized like identical `fetch` calls. The plan query also selects all plan columns and images (`src/lib/plans.ts:31-43`). This can multiply database round trips per uncached request.
- **Recommended fix:** Measure deployed TTFB and database query counts first. Use request-scoped memoization for shared detail reads; consider bounded revalidation or caching only for public published content, with explicit invalidation after admin changes. Keep private admin pages dynamic.
- **Complexity:** Medium. **Timing:** Can wait unless deployed latency or query cost is poor.

### F9 — Cover images bypass Next.js image optimization

- **Category / severity / status:** Performance / **Medium** / confirmed implementation; user impact depends on external image sizes.
- **Evidence:** `src/components/plan-image.tsx:27-35` sets `unoptimized` for all covers, so `sizes` does not produce responsive transformed variants. URL covers depend on third-party hosts, and a prior development cover returned 403 as recorded in `docs/ARCHIMART_CONTEXT.md`. The image fallback handles failure but cannot reduce byte size. The upload path is postponed with R2.
- **Recommended fix:** Measure real cover transfer sizes and failures on the deployment. Require durable, appropriately sized source images for URL entry now; when storage is available, review an allowlisted image optimization strategy or pre-sized variants. Do not broadly proxy arbitrary hosts without a security and cost review.
- **Complexity:** Medium. **Timing:** Verify live cover reliability before launch; optimization can wait for measured need.

### F10 — Unused root data provider and dormant UI increase maintenance cost

- **Category / severity / status:** Maintainability / **Low** / confirmed unused source paths; exact bundle cost not isolated.
- **Evidence:** `src/app/layout.tsx:6,55` wraps every page with `src/app/providers.tsx:1-11`, which creates a React Query client. Source search found no `useQuery` or `useMutation` in active app code. `src/app/page.tsx:1-6` imports six landing sections; additional files such as `src/components/landing/ArchiAI.tsx:1`, `BuildTrack.tsx:1`, and `Waitlist.tsx:1` are not imported by active routes. `package.json:24-51,58-75` retains many UI libraries used only by dormant components or not at all.
- **Recommended fix:** Remove the root provider if still unused, then prune dormant out-of-scope components and their proven unused dependencies in a separate cleanup. Use import analysis and a build diff; avoid broad abstraction work.
- **Complexity:** Small to medium. **Timing:** Can wait until after launch.

The review also compared the plan, professional, application, and enquiry validation and action patterns. `src/lib/require-admin.ts:10-20` already centralizes authorization, and the Zod schemas in `src/lib/plan-input.ts:1`, `src/lib/professional-input.ts:1`, `src/lib/professional-application-input.ts:10-23`, and `src/lib/enquiry-input.ts:3-13` keep domain rules separate. The small repeated parse and error-message blocks in `src/app/admin/plans/actions.ts:30-42` and `src/app/admin/professionals/actions.ts:16-32` do not justify a new shared abstraction at V1 scale. Write errors are intentionally generic for public forms (`src/app/enquiries/actions.ts:71-88`; `src/app/professionals/apply/actions.ts:48-54`), while admin writes rethrow unexpected errors to the route error boundary; no concrete information leak was established from that difference.

### F11 — Application review can diverge from a linked profile

- **Category / severity / status:** Reliability / **Medium** / confirmed state-transition gap; no production incident observed.
- **Evidence:** Review input permits any of four statuses (`src/lib/professional-application-input.ts:44-53`). The update in `src/app/admin/applications/actions.ts:28-37` changes status by ID without checking `professionalId` or prior status. An approved application already linked to a profile can therefore be set back to `submitted` or `rejected`, while its profile remains independent. `reviewedAt` is replaced on every save, which can obscure the final decision date needed by `docs/DATA_RETENTION.md:9-12`.
- **Recommended fix:** Define allowed transitions and the meaning of changing a linked application. Preserve final decision evidence in the restricted manual log until a schema-backed history is approved; prevent inconsistent transitions in the action and give admins a clear message.
- **Complexity:** Medium. **Timing:** Before routine V1 application review at scale; manual review can mitigate at initial launch.

### F12 — Retention operations and backup settings are still manual unknowns

- **Category / severity / status:** Reliability / **Medium** / confirmed operational gap, not a code vulnerability.
- **Evidence:** `docs/DATA_RETENTION.md:1-3,26-39` states that no deletion UI or automated deletion exists and actual backup retention is unverified. The schema has `enquiries.updated_at` but no closure timestamp (`src/db/schema.ts:221-244`), while `src/app/admin/enquiries/actions.ts:31-35` only updates status. The approved policy relies on a restricted status and review log rather than inventing dates.
- **Recommended fix:** Assign the designated reviewer, establish the restricted log and approval record, confirm backup settings, and practice the reviewed manual procedure only after separate authorization. Do not infer closure dates from later edits.
- **Complexity:** Small operational setup; medium for eventual tooling. **Timing:** Establish manual process before public V1 launch; tooling can wait.

### F13 — Dynamic pages have no route-level loading boundary

- **Category / severity / status:** Performance / **Low** / confirmed source omission; user-perceived impact unmeasured.
- **Evidence:** The public catalogue pages await database queries before rendering (`src/app/plans/page.tsx:13-15`; `src/app/professionals/page.tsx:23-25`), and no `loading.tsx` or route-level `Suspense` boundary exists under `src/app`. A slow Neon read could delay visible content. There is no evidence yet of slow deployed responses.
- **Recommended fix:** Measure deployed navigation and TTFB first. If users experience waiting, add small route-level loading states or stream noncritical sections; avoid extra client state solely to show a spinner.
- **Complexity:** Small. **Timing:** Can wait for live performance evidence.

## Local measurements and validation

- `npm run lint` and `npm run typecheck` passed. No feature tests were rerun because this assessment made no application changes and prior development workflow testing is recorded in `ARCHIMART_CONTEXT.md`.
- Existing `.next` build artifacts measured **2.0 MiB** of static files and **3.2 MiB** of server files. Its four root client chunks total **439 KiB raw / 130 KiB gzip**. These are file totals from an existing local Webpack build, not a per-route transfer measurement, Core Web Vitals result, or a fresh production build. Individual route chunks were about 4–8 KiB on disk in this artifact; shared chunks dominate. The 624 KiB source logo (`src/assets/archimartng-logo-transparent.png`) is transformed by Next Image, so its source size alone does not establish transferred bytes.
- Query indexes exist for publication/status and creation (`src/db/schema.ts:87-92,162-169,207-211,245-249`). The public lists order by `published_at` (`src/lib/plans.ts:28`; `src/lib/professionals.ts:23`), which is not the indexed second column; no query plan or row counts were inspected. Benchmark with realistic data before adding an index or migration.
- Required deployed checks remain: security and cache headers, session cookie attributes, auth throttling across instances, branch and origin binding, page TTFB/Core Web Vitals, per-route transferred JavaScript and image bytes, catalogue size, query plans, and the published image load rate. This audit did not contact production or change infrastructure.
